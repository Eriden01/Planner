# Аудит кода Planner — 11 октября 2026

## Вывод

Planner уже является насыщенным рабочим приложением, но архитектура пока остаётся прототипной: почти вся логика зависит от одного изменяемого объекта `db`, глобальных переменных и прямых обновлений DOM. Следующий этап стоит посвятить надёжному хранению и границам модулей. Добавление новых крупных функций сейчас будет увеличивать стоимость проверки и риск регрессий.

Начат первый этап: разделение файлов, устранение воспроизводимых ошибок, локальные оптимизации и регрессионные тесты. Полное переписывание интерфейса, переход на React/TypeScript и новый сервер не выполнялись. Они не являются предварительным условием для исправления текущих проблем.

## Объём проверки и ограничения

- Исходный `index.html`: около 6922 строк, 2 217 180 байт; разметка, стили, JavaScript и base64-графика находились вместе.
- Просмотрены подсистемы JavaScript: миграции, сохранение, история, восстановление, Supabase, аккаунт, календарь, проекты/заметки, деньги/траты, тренировки, таймер/аналитика, портфолио, аватар, обучение и мобильный viewport.
- Все текстовые ресурсы включены в инвентаризацию; JavaScript проверен парсером, локальные ссылки проверены на существование. CSS загружен и разобран браузером. Проверены отсутствие повторяющихся DOM ID и переходы по десяти разделам.
- Выполнены браузерные сценарии на синтетических данных в отдельном профиле Chrome, а также реальная офлайн-перезагрузка через service worker. Есть снимки desktop 1440×1000 и mobile viewport 390×844.
- Это не утверждение, что каждая строка исполнена тестами или все ошибки найдены. Все сочетания данных, визуальные состояния и устройства не проверены. Mobile viewport не заменяет физические iPhone/Android.
- Нет доступа к конфигурации живого Supabase: RLS, ограничения таблицы, Realtime, восстановление пароля и параллельная работа реальных устройств не проверялись. Облачные тесты используют имитацию ответов. Docker здесь отсутствует.

Тест проверяет появление занятия в «Сегодня». Уже сохранённую категорию `other` автоматически не переписываем: исходное намерение пользователя неизвестно. |

Это закрывает обнаруженный путь попадания некорректных строк времени в HTML и падение при неверном индексе дня. Остальная вложенная схема требует дальнейшего усиления. |

Основной код: `frontend_ts/public/js/app.js`. Публичные ключи Supabase, пользовательские данные, экспортный формат schema 23 и адрес размещения не менялись.

## Оптимизация

1. **Файлы разделены.** Разметка — `public/index.html`, логика — `public/js/app.js`, стили — `public/styles/app.css`, графика — `public/images/profile-89aa5b0d3614.png`. Изображение извлечено без перекодирования; CSS-содержимое сохранено, кроме ссылки на изображение. Главный JS пока остаётся одним файлом с общей областью видимости — это промежуточный шаг, а не завершённая модульная архитектура.
2. **HTML уменьшен с 2 217 180 до 96 275 байт — примерно на 95,7%.** Общий объём ресурсов уменьшился существенно меньше: логика, стили и картинка всё ещё нужны. Это измерение размера файлов, не обещание ускорения в 23 раза. Картинка занимает 1 143 194 байта и остаётся кандидатом на отдельную оптимизацию.
3. **SDK облака больше не блокирует разбор страницы.** Используется уже существовавший асинхронный загрузчик с таймаутом. Локальный интерфейс доступен при недоступном CDN.
4. **Денежный форматтер создаётся один раз.** Вместо нового `Intl.NumberFormat` для каждой суммы используется общий экземпляр.
5. **Убраны соседние повторные вызовы `renderFood()` и `renderMoney()`.** `renderMoney()` уже обновляет траты; второй обход и повторное создание обработчиков не нужны.
6. **Месячный календарь группирует события за один проход.** До этого массив всех событий фильтровался отдельно для каждого из 42 дней.
7. **Перенесённые задачи проверяются через `Set`.** В `taskAreaEvents()` больше нет вложенного поиска по всему календарю для каждой перенесённой записи; сохранено поведение исключения промежуточных звеньев.
8. **Скрытый профиль не пересчитывает всю аналитику при каждом статусе синхронизации.** Секундный таймер не перерисовывает DOM скрытой вкладки.
9. **PWA кеширует целиком согласованный комплект локальных ресурсов.** Установка не ждёт CDN; SDK кешируется отдельно по требованию. В новый кеш больше не попадают произвольные GET-ответы того же origin. Обновление ждёт закрытия старых вкладок.

## Что остаётся важным

### P1 — согласованность данных

**Две вкладки одного аккаунта могут перезаписать изменения друг друга.** Обработчик `storage` сейчас синхронизирует тему, но не `db`. `save()` читает последнее сохранённое значение для истории, однако записывает свой объект из памяти без сравнения его исходной версии. Сценарий: обе вкладки загрузили состояние A; первая добавила B; вторая добавила C к старому A и сохранила A+C. Нужен единый протокол транзакций и конкуренции между вкладками: ревизия, обнаружение устаревшего снимка, объединение или явный конфликт. Проверить на двух вкладках, а не только двумя функциями.

**Редактор заметки не проверяет исходную версию записи.** В отличие от обучения/портфолио, `flushProjectNote()` сравнивает только текущие поля и не хранит версию текста, с которой открыт редактор. Если облако обновило запись во время редактирования, старый текст формы может перезаписать свежий. Нужны сохранение базовой версии, независимый черновик и конфликт на уровне записи.

**Удаление календарных событий обрабатывается несколькими путями.** Удаление подзадачи сохраняет таймер и связанные записи, но `clearViewedWeek()` просто фильтрует календарь. При исчезновении события `drawTimer()` очищает активный таймер без сохранения накопленного интервала; также могут оставаться привязанные тренировки. Следующий шаг: одна команда удаления событий с обновлением связей и сохранением таймера до удаления. Тесты: одиночное событие, серия, неделя, переносы, активная сессия.

**Отметка тренировки не ведёт дату завершения единообразно.** `syncWorkoutToCalendar()` присваивает `status/done` напрямую и не использует общий механизм `completedAt`. Аналитика, зависящая от даты выполнения, может расходиться. Следует сделать одну команду изменения статуса, используемую календарём и тренировками.

### P1 — хранение и серверный контракт

**Один JSON содержит всё, включая вложения.** Каждый `save()` сериализует состояние, сравнивает домены, готовит историю, резерв и облачную версию. До восьми изображений на работу и PDF до 1 МБ многократно копируются. История ограничена по длине JSON, но это не точная квота браузера; запись истории может тихо не состояться. Undo после первой успешной записи стал надёжнее, но основная запись и история всё ещё не являются одной атомарной транзакцией.

Предлагаемая цель: IndexedDB для локальных записей, черновиков и транзакционной истории; бинарные вложения — отдельно, с ID и ссылками. LocalStorage оставить для небольших настроек. IndexedDB поддерживает большие структурированные данные и файлы/Blob: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API). Миграция должна копировать данные, проверять результат и сохранять исходный JSON до подтверждения; простого удаления старого ключа быть не должно.

**Серверная схема не зафиксирована в репозитории.** Нужны миграции таблицы `planner_state`, уникальность `user_id`, проверка ревизии, ограничения и RLS. Публичный клиентский ключ сам по себе не секрет; безопасность определяется серверными правилами. Проверять доступ от двух разных пользователей следует в тестовом Supabase-проекте: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). В этом аудите база не опрашивалась и не изменялась; отсутствие RLS не утверждается.

**Границы доверия при импорте неполные.** Есть ограничения глубины, числа узлов, ID, дат, времени и защита от опасных ключей. Но вложенные структуры обучения, таймер, настройки и некоторые дополнительные числовые поля валидируются не полностью. Нужна единая схема каждой сущности, включая необходимые поля, размер текста, перечисления, неотрицательные числа, ссылки на другие записи и совместимые старые версии.

### P2 — поддерживаемость и быстродействие

- По инвентаризации около 378 объявленных функций, 80 присваиваний `innerHTML`, 70 вызовов `save()` и 154 `!important` в CSS. Это ориентиры сложности, а не самостоятельные ошибки.
- Найдены 17 кандидатов в неиспользуемые функции, включая старые графики фокуса и прежнюю обработку аватара. Они перечислены в `audit/static-inventory.json`. Не удалены автоматически: требуется проверить косвенные вызовы и продуктовую необходимость.
- CSS многократно переопределяет одни и те же селекторы, в том числе внутри разных media queries. Объединять только с визуальными проверками всех тем и размеров; одинаковое имя селектора не означает лишнее правило.
- Есть повторные проходы по календарю/времени внутри профиля и аналитики, глобальные селекторы и полные перерисовки скрытых разделов. После отделения состояния нужно обновлять только затронутый видимый раздел и общие индикаторы.
- Перед измерениями скорости подготовить наборы 100 / 1000 / 10 000 событий, длинные заметки, 1000 сессий, вложения. Измерять открытие раздела, сохранение и длинные задачи main thread. Не ускорять запись за счёт потери гарантии сохранения.
- `Premium` частично определяется email на клиенте. Пока это подпись интерфейса; если появятся платные права, их нужно выдавать и проверять на сервере.

## Предлагаемый порядок дальнейшей работы

| Этап | Работа | Критерий готовности |
|---|---|---|
| 1. Надёжность | Две вкладки, конфликты заметок, единое удаление событий, статусы тренировок, полная валидация | Для каждого сценария есть воспроизводящий тест; данные/таймеры не пропадают |
| 2. Границы кода | `core/state`, `storage`, `sync`, `calendar`, `finance`, `projects`, `focus`, `learning`, `portfolio`, `profile`, `ui` | Разделы вызывают команды/сервисы вместо прямой записи в глобальный `db`; повторные бизнес-правила устранены |
| 3. Хранение | IndexedDB, отдельные вложения, единые миграции, транзакционная история | Перенос старого экспорта проверен; есть восстановление и откат; большие вложения не копируются при каждой правке заметки |
| 4. Облако | Зафиксированная схема/RLS, тест двух аккаунтов и двух устройств, очередь операций и обработка конфликтов | Проверены отсутствие чужого доступа, офлайн-правки, повторы и гонки ревизий |
| 5. Производительность | Измерения на больших наборах, индексы, ограниченные перерисовки, чистка CSS и мёртвого кода | Есть сравнение до/после на одинаковых данных, без ухудшения сохранения |
| 6. Выпуск | Версия сборки, автоматические проверки, журнал изменений, проверка обновления PWA | Проверены установка, обновление, офлайн и возврат к предыдущему релизу |

На ближайшую итерацию рекомендую этап 1 и начало этапа 2. После выделения чистой бизнес-логики можно постепенно добавить TypeScript, начиная с моделей данных и протокола синхронизации. Выбор UI-фреймворка имеет смысл обсуждать отдельно после стабилизации этих границ.
